# ADR-001 — Enterprise Asset Registry (EA-001)

**Status:** Implemented, not yet deployed. First ADR in this repository — no prior ADR numbering convention existed to follow (checked `docs/`; the ED-series decision records live in `master-growth-os`, not here).

**Amendment (Production Verification pass, same day):** the Enterprise Design Authority's architecture review returned "Accepted with observations" — no schema/domain redesign. Four correctness/hardening fixes were made to migration 007 in place (not yet applied anywhere, so no follow-up migration was needed) and to `repository.ts`, none of which change any table shape, function signature's return type, RLS posture, or the extensibility mechanism in decisions 1–7 below:
- `update_enterprise_asset`, `archive_enterprise_asset`, `restore_enterprise_asset` now take a `FOR UPDATE` row lock on their initial read, closing a concurrent-mutation race at the DB level.
- `create_enterprise_asset_relationship` now only writes its `RelationshipCreated` audit record and event on the *first* creation of a (source, target, type) triple — a repeat call that only updates metadata (the existing `ON CONFLICT DO UPDATE` upsert behavior, unchanged) no longer produces a second, misleading `RelationshipCreated` entry.
- `repository.ts`'s error mapping now passes the real Postgres error message through to `AssetNotFoundError`/`UnknownAssetTypeError` instead of re-templating around a caller-supplied ID — fixes a real bug where a relationship's *target*-not-found error was reported citing the *source* ID.
- Added DB-level `CHECK` length/size constraints (name/description/owner/business_domain/relationship_type length caps, country format, metadata byte-size cap) mirroring the existing app-layer limits — defense-in-depth for any caller that invokes the RPC functions directly, bypassing the API's validation layer. `description` also gained an app-layer length cap it was previously missing (type-checked but unbounded).

Full detail in [EA-001_PRODUCTION_READINESS_REPORT.md](./EA-001_PRODUCTION_READINESS_REPORT.md).

## Context

EA-001 asked for a permanent Enterprise Foundation capability: the authoritative registry for every enterprise asset (Enterprise, Product, Operating System, Shared Service, Capability, Workspace, Team, Automation, Knowledge Asset, and any future type), with immutable identifiers, relationships, audit, and events — explicitly not a product feature, and explicitly no UI/dashboard/reporting.

**Repository Discovery performed before writing any code** (per this programme's standing gate): the `projects` table (migration 001) is a narrow monitoring table — 6 columns, no lifecycle/metadata/relationships/audit — used by Portfolio Health, Alerts, and Deployment Summary. `enterprise-registry.ts` (D-006) is a static, no-DB, TypeScript config array describing the 6-7 businesses in the portfolio, with no audit/events/relationships either. Neither overlaps with what EA-001 asks for; both are left untouched. This is genuinely new, additive capability.

## Decisions

**1. Asset type is a lookup table, not a CHECK constraint.** `enterprise_asset_types(code, prefix, label, ...)` is seeded with the 9 required types. Adding a 10th type in the future is one row insert — the spec's explicit requirement ("design the model so additional asset types can be added without schema redesign") is satisfied literally, not just in spirit. `enterprise_assets.asset_type_code` is a foreign key into it. Validity of a submitted `asset_type_code` is checked live against this table (`assetTypeExists()` / the `create_enterprise_asset` function), so a newly inserted type is usable immediately with no code deploy.

**2. Status vs. Lifecycle Stage are two different, deliberately differently-enforced fields.** `status` (`active | inactive | archived`) is the operational/soft-delete state — small, stable, closed set, enforced with a DB `CHECK` constraint. `lifecycle_stage` (`concept | building | pilot | live | growing | scaling | deprecated | retired`) mirrors the `BusinessStage` vocabulary already used by `enterprise-registry.ts`, extended with `deprecated`/`retired` since assets outlive individual businesses — validated at the application layer (`validation.ts`), not DB-enforced, so its vocabulary can also evolve without a migration. This is a lighter version of decision #1's reasoning, applied more cheaply since the spec didn't explicitly demand type-level extensibility for this field.

**3. Every mutation is a single Postgres function; mutation + audit + event commit in one transaction.** `create_enterprise_asset`, `update_enterprise_asset`, `archive_enterprise_asset`, `restore_enterprise_asset`, `create_enterprise_asset_relationship` each do their primary write and their audit-log insert (and, where applicable, event-outbox insert) inside one `plpgsql` function body — Postgres functions are transactional, so there is no window where the asset table and the audit trail can disagree. The alternative (writing audit/events from the application layer after a separate insert/update call) was rejected because it reintroduces exactly the dual-write gap this capability exists to prevent.

**4. Events (outbox table) are a deliberately narrower set than Audit (compliance log).** The spec names exactly 5 event types (`AssetCreated`, `AssetUpdated`, `AssetArchived`, `RelationshipCreated`, `LifecycleChanged`) — `AssetRestored` is not among them, so `enterprise_asset_events.event_type` does not include it, even though `enterprise_asset_audit_log.action` does (audit's own requirement — "every mutation must create an audit record" — has no such carve-out). `enterprise_asset_events` is a polling-friendly outbox table (`consumed_at` marker) rather than a live pub/sub bus: no message broker exists anywhere in this codebase, and wiring one is out of EA-001's explicit scope ("no dashboard... no digital twin"). This is V1 infrastructure the future Enterprise Graph consumer can poll; a real bus is a later decision, not made here.

**5. `PATCH` replaces `metadata` wholesale, not a deep merge.** Simpler and more predictable than field-level JSON merge semantics; documented in the API reference so callers know to send metadata's full desired shape.

**6. RLS: read-all policy on every new table, writes stay service-role only.** This exactly matches migration 005's platform-wide fix (EI-001) — this repository has no authentication layer anywhere yet, so every existing table is already anon-key readable. Enabling RLS with a permissive `select using (true)` policy (rather than leaving RLS off) avoids repeating the RLS-enabled-but-zero-policies bug that silently blanked every read across D-002–D-007 before EI-001 caught it. This is a known, disclosed, platform-wide limitation — not something newly introduced by EA-001 — including for the audit log, which in a system with real authentication would likely be more restricted.

**7. Actor is caller-supplied, not authenticated.** There is no auth middleware anywhere in this codebase (confirmed by earlier Repository Discovery work, e.g. EA0006 Phase 1, EI-001). `actor` is an optional field on every mutation request, defaulting to `'system'` when omitted. This is honestly a trust boundary gap: nothing stops a caller from claiming to be anyone. It is not a regression EA-001 introduces — it is the same gap every other mutation endpoint in this repository already has — but it means the audit log's `actor` column should not be treated as a verified identity until the platform has real auth.

## Consequences

- New tables: `enterprise_asset_types`, `enterprise_assets`, `enterprise_asset_relationships`, `enterprise_asset_audit_log`, `enterprise_asset_events`, `enterprise_asset_id_counters`. New functions: `generate_enterprise_asset_global_id`, `create_enterprise_asset`, `update_enterprise_asset`, `archive_enterprise_asset`, `restore_enterprise_asset`, `create_enterprise_asset_relationship`, `set_enterprise_assets_updated_at` (+ trigger).
- New dependency: `vitest` (devDependency only) — this repository had zero test infrastructure before EA-001, and "Automated Tests" is an explicit required deliverable. No production dependency was added.
- Nothing existing was modified except `src/types/index.ts` (one new re-export line) and `package.json` (two new scripts + the new devDependency).

## Open items, honestly disclosed

- **Migration 007 has not been run against a live database this session** (no Supabase credentials/connection available here). The SQL was written and manually reviewed; the atomic-function business logic was additionally mirrored line-for-line in an in-memory TypeScript fake and exercised by 63 automated tests (see the Evidence Package), but that is not a substitute for running the real migration once credentials are available. **Do not treat this capability as production-verified until migration 007 has actually been applied and smoke-tested against the real Supabase project.**
- No endpoint to list or manage asset types was requested or built — the 9 seed types are the only way in for now; adding a 10th requires a direct DB insert (by design, per decision #1, but there's currently no API surface for it).
- `relationship_type` is an intentionally open vocabulary (the spec didn't enumerate one, unlike asset types) — nothing stops a caller from inventing a new relationship type per request. `SUGGESTED_RELATIONSHIP_TYPES` in `constants.ts` is guidance only, not enforced.
