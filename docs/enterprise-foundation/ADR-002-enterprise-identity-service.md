# ADR-002 — Enterprise Identity Service (EA-002)

**Status:** Phase 1 implemented (2026-07-28), following Enterprise Design Authority Review approval (Result: APPROVED, L2 – Design Approved, Phase 1 implementation only). Migration, types, repository layer, API routes, and tests exist and pass (130/130 including EA-001's 68); migration not yet applied to a live database — see [EA-002_PRODUCTION_READINESS_REPORT.md](./EA-002_PRODUCTION_READINESS_REPORT.md). Full build evidence in [EA-002_EVIDENCE_PACKAGE.md](./EA-002_EVIDENCE_PACKAGE.md). This ADR's design decisions below were not altered during implementation; the Design Specification remains at [EA-002_ENTERPRISE_IDENTITY_DESIGN_SPECIFICATION.md](./EA-002_ENTERPRISE_IDENTITY_DESIGN_SPECIFICATION.md), the same relationship [ADR-001](./ADR-001-enterprise-asset-registry.md) has to EA-001.

**Amendment (2026-07-28, at implementation):** Founder Decisions closed the four items this ADR and its Design Spec had left open: `GROUP` identity type — deferred, not implemented; EA-001 `owner`/`actor` referencing Identity — deferred, no EA-001 modification; RLS — dedicated (non-read-all) posture, Service Role/Public/Authenticated tiers implemented, Enterprise Admin tier disclosed as not implementable without a new Access Control capability (see Evidence Package); global ID prefix — `ID-`, approved and implemented. One real design-fidelity bug was caught during implementation and fixed, not silently absorbed: `activate` and `reactivate` share the target state `active`, so an EA-001-archive/restore-style "idempotent if already at target" shortcut would have let `reactivate` silently succeed on an identity that reached Active via `activate` (never suspended) — a transition this ADR's own state diagram does not offer. Fixed by making `activate`/`reactivate` strict (no idempotent shortcut) while `suspend`/`deactivate`/`archive` keep it, since only the latter three have a uniquely-producing predecessor state. Full detail in the Evidence Package's "Implementation-phase decisions."

## Context

EA-002 asked for the design of an Enterprise Identity Service — the record of who/what can act within MasterOps — explicitly excluding authentication, login, and permissions, and explicitly required to integrate cleanly with EA-001 while preserving loose coupling.

**Reconciliation with existing platform documentation:** D-007's Shared Services Catalogue (`src/lib/shared-services-catalogue.ts`) already carries an "Enterprise Identity" entry whose `purpose` field reads *"Establish who is acting within the Enterprise **and enforce access control** across every product and shared service"* — conflating identity with access control into one undifferentiated future capability. EA-002's own instructions ("Do NOT implement permissions... Focus on enterprise identity only") are narrower than that framing. This ADR's decisions below deliberately build the narrower thing D-007 gestured at, not the broader one its wording implied. The catalogue entry itself is not edited by this design assignment (see the Design Specification §9, "Housekeeping").

## Decisions

**1. Identity type is a lookup table, not a closed enum — same mechanism as EA-001.** `enterprise_identity_types` seeded with `PERSON`, `SERVICE`, `EXTERNAL`. A `GROUP` type was considered and deliberately deferred (Design Spec, Open Question 1) rather than spuriously added now — it risks duplicating EA-001's existing `TEAM` asset type, and that overlap should be resolved by a real use case, not guessed at.

**2. Identity lifecycle is its own vocabulary (`provisioned → active → suspended → deactivated → archived`), not a reuse of EA-001's `lifecycle_stage`.** EA-001's stages (`concept → ... → retired`) measure asset/product maturity; an identity doesn't mature, it's provisioned and eventually retired, and it needs a `suspended` state (reversible, temporary) that has no asset-registry analogue. Reusing EA-001's enum would have been copying a word without the underlying concept matching — rejected specifically because it would look like a shared vocabulary the two systems don't actually share.

**3. Exactly one integration point with EA-001: an optional, nullable `enterprise_identities.asset_id` foreign key, read-only from the Identity Service's side, invisible from EA-001's side.** Discovered while re-reading EA-001's actual schema (not assumed): `enterprise_asset_relationships` requires both sides of a relationship to already be `enterprise_assets` rows, which rules it out as an integration mechanism without forcing every identity to also be an asset — a change that would corrupt EA-001's own domain model, precisely the thing the recent EA-001 Production Verification pass was instructed to protect ("Do NOT redesign EA-001"). The alternative considered and rejected: modeling identities *as* EA-001 asset rows (using EA-001's extensibility mechanism to add an `IDENTITY` asset type). Rejected because an identity is an actor, not an inventory item, and conflating the two ideas — even though EA-001's extensibility mechanism could technically absorb it — would be using a tool because it's available, not because it fits. The one-directional FK keeps EA-001 fully independent: it has zero code, schema, or test changes as a result of this design, and would remain so even if this design were never implemented.

**4. Multi-tenancy is a soft (non-FK) reference to `enterprise-registry.ts`'s existing business slugs, not a new `tenants` table.** `business_scope` is nullable text; `null` means enterprise-wide (e.g. the Founder, a MasterOps-internal automation). No FK is possible because `enterprise-registry.ts` is a static TypeScript config array by D-006's own explicit decision ("configuration-driven, no database") — building a real tenants table now would mean re-opening that decision inside an identity-design assignment, which is out of scope. Consequence, stated directly: **this service's remit is MasterOps-internal and cross-portfolio-operator identities, not each product's own end-customers** — ELBOLD's customers, for instance, stay ELBOLD's own concern (Layer 4 per the Charter), with their own separate auth and database, unaffected by this design.

**5. No credential or secret storage, ever, in this service — a hard non-goal, not just an unstated omission.** Stated explicitly in the Design Spec (§8) as a line future implementers should not cross "for convenience." Authentication is a separate, future, explicitly out-of-scope service that would *consume* Identity records, not extend this schema.

**6. RLS posture is explicitly NOT inherited from EA-001's read-all pattern.** EA-001's migration 007 enables RLS with a permissive `select using (true)` policy on every table, justified there because nothing in `enterprise_assets` is PII (ADR-001 decision 6). `enterprise_identities` will hold real names/emails for `PERSON`/`EXTERNAL` types — copying the read-all pattern here without re-evaluating it would be treating "consistency with EA-001" as more important than the actual different risk profile. This ADR does not decide the correct RLS posture (that's an implementation-phase decision) — it decides that EA-001's answer must not be copied by default.

**7. Audit-log immutability (inherited principle from EA-001: never hard-delete, `before`/`after` snapshots are permanent) is flagged, not silently adopted wholesale.** A `PERSON`/`EXTERNAL` identity may need genuine erasure (e.g. GDPR) in a way an enterprise asset never does. This ADR names the tension (Design Spec §8) rather than resolving it, because resolving it requires a real decision (e.g. redacting audit payload contents while preserving the audit *event* itself) that belongs to whoever implements this, informed by whatever data the service actually ends up holding.

## Consequences

- Zero changes to EA-001 (schema, code, tests, docs) result from this design. It can be implemented, deferred, or abandoned without EA-001 needing to change either way — the loose-coupling requirement is satisfied structurally, not just by intention.
- Two future services (Authentication, Access Control) are explicitly named as consumers of Identity records without being designed here — this ADR's scope boundary is load-bearing for both of them.
- Two open questions (GROUP-vs-TEAM overlap; whether EA-001's `owner`/`actor` should eventually reference Identity records) are deliberately left unresolved rather than guessed at, because guessing wrong on either would be expensive to unwind later (the second one in particular would create a dependency EA-001 doesn't currently have).

## Open items, honestly disclosed

- This design has not been reviewed by an Enterprise Design Authority pass the way EA-001 was — it is itself the document awaiting that review, not a retrospective account of one.
- No implementation timeline is proposed beyond the phase ordering in the Design Spec §9 — sequencing/priority against the rest of the programme's backlog is a Founder decision, not this ADR's to make.
- D-007's Shared Services Catalogue entry for "Enterprise Identity" still describes the old, broader (identity + access control) framing as of this ADR's writing — a known, named documentation drift (Design Spec §9 Housekeeping), not yet corrected.
